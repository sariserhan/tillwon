- [x] **Disqualification no longer permanently freezes the campaign.** `rejectClaim` only ever marked the *claim* disqualified — the campaign stayed stuck in `winner_pending` forever, with no way to spin again, contradicting product policy (resolved 2026-08-06: "the campaign resumes... and the next entry to reach it wins") and the rules page's own admission that this was "not yet implemented." Implemented the `resume_campaign` policy (the only one of the schema's three `disqualificationPolicy` options that had clear enough product guidance to build): flips the campaign back to `live`, clears `winningSpinId`/`potentialWinnerUserId`, and — this part isn't obvious — decrements the winning shard's spin-count by exactly 1. That last step is load-bearing: a win requires the shard's running count to land exactly on `winningCount`, that count never resets, and the disqualified spin already consumed the only moment it could ever equal `winningCount` again. Without un-consuming it, the campaign would report itself `live` while the sealed target became permanently unwinnable — a real bug my first pass had, caught by a test that actually exercised a second spin against the resumed campaign rather than just checking the status flip. `select_alternate` and `end_campaign` are unimplemented; campaigns configured with either keep the old frozen behavior until those get their own design pass (see "Next design decision" below).

- [x] **`app/rules/page.tsx` copy updated** to stop saying the resume mechanism is "not yet implemented" — it now says the resume-to-live mechanism is implemented but not yet reviewed by counsel (still true, still gates publishing the specific wording). Also updated the internal dev comment above it, which had explained in detail exactly why the old engine couldn't deliver this mechanism (the shard-count-never-resets problem) — that comment now records that the gap is closed and how.
- [x] **`select_alternate` and `end_campaign` disqualification policies, implemented.** `end_campaign` marks the campaign `cancelled` and audits it — the simple one. `select_alternate` re-seals a genuinely new commitment (same winning shard, `winningCount + 1`, a fresh nonce) rather than reusing `sealTarget` (deliberately one-time-only), verifies the *current* commitment before touching anything (same discipline `approveClaim` uses), and audits only the old/new commitment hashes — never the raw shard/count/nonce, matching `sealTarget`'s own "the hash is logged, the target is not" principle. Needed real crypto randomness for the new nonce, which this codebase deliberately draws outside a mutation transaction (see `winnerEngine.ts`'s `activateCampaign`) — so `rejectClaim` became an action too, the same restructuring `registerUploadedDocument` went through earlier (client call site: `useMutation` → `useAction`). Tested end-to-end the same way `resume_campaign` was: a real second spin actually winning against the new target, not just the state-flip.
- [x] **Admins can request more info instead of only Approve/Reject.** `claims.status` had eight schema-defined literals (`more_info_required` among them) that no code ever used — the only real path for a submitted claim was Approve or Reject, so any fixable problem (a blurry photo, wrong document type) forced the admin into approving anyway or disqualifying a legitimate winner. Added `admin.requestMoreInfo(claimId, message)`, which sends a claim back to `more_info_required` with the admin's message; the claimant's page shows that message and lets them re-upload/resubmit (the upload/register/submit gate now accepts `potential_winner` *or* `more_info_required`); resubmission clears the message and returns to `under_review`. The admin queue (`listPendingClaims`) shows these claims too (with a new Status column) rather than letting them silently vanish from view. The other unused status literals (`notification_sent`, `claim_started`, `documents_requested`, `prize_processing`, `prize_shipped`, `prize_delivered`, `completed`) are genuinely future scope — email notifications and physical-prize fulfillment tracking, nothing to build without real requirements behind them yet, same as sound/sponsor-video.
- [x] **The paused reel shows the actual winning result, frozen, with when it happened, to every visitor — not just a text notice.** Previously `CampaignPausedNotice` (what everyone but the winner sees once a campaign hits `winner_pending`) was text-only. `convex/campaigns.ts`'s `getActiveCampaign` now also returns the winning spin's visual `symbols` and its timestamp once `winningSpinId` is set — safe to expose publicly because the visual outcome is never the sealed secret (only *which* shard/count wins is sealed; a jackpot always shows the same symbols by construction). The notice renders those symbols at rest in the same `FlapDrum` tiles the live spin uses (no animation — `falling` stays `false`), with a formatted date and time underneath. Verified live in a browser (this page needs no auth, so unlike most of this session's frontend work it wasn't blocked by Turnstile): seeded a real `winner_pending` state via a temporary Convex mutation, confirmed the frozen "7 7 7" reel and timestamp render correctly, then reverted the temporary mutation and its test data.

## Looked into, deferred

- **`endAt` (tier 5-6 hard end date) is unenforced.** `convex/schema.ts` has the field, `spinExecute` never reads it, and there's no cron in this project — a tier 5-6 campaign would spin forever past any stated end date. `PRODUCT.md` frames this as a hard legal requirement (surety bond can't stay outstanding indefinitely), but building it raised a real conflict with the "till won" promise (does an unwon tier 5-6 campaign ever end without awarding its prize, or does something guarantee a winner by the deadline — a materially bigger mechanism). Discussed and deferred rather than guessed at: no deadline enforcement gets built until this is actually resolved, which likely needs the counsel review `PRODUCT.md` already says is pending for tiers 5-6 generally.

Every SDD task in this feature hit Clerk's Turnstile bot-protection wall and verified around it (tests + type-checking + shape review) instead of a live pass. The new `/documents` HTTP action was smoke-tested live and unauthenticated (route reachable, argument validation, CORS/OPTIONS all correct) but its authenticated success path — an admin actually viewing a document through it — needs the same browser pass as the rest of the flow. Unblock with Clerk dev bot-protection off, or `+clerk_test` addresses. **Also covers the new campaign-admin flow** (`/admin/campaigns/new` → detail page → Activate): tried a `+clerk_test` sign-up during this task specifically to unblock this, and hit the same Cloudflare Turnstile challenge (it resets rather than clears on click) — confirming this needs the bot-protection-off route, not just a different test-email trick. Verified instead via the full backend test suite (130 tests, including the atomic create/list/detail/activate path and the single-active-campaign race guarantee), `tsc --noEmit`, `next build`, and a live unauthenticated pass confirming both new routes fail closed through the existing `AuthErrorBoundary` (a malformed campaign ID 404s the same way the pre-existing `/admin/claims/[claimId]` already does with a malformed claim ID — not a regression).
- [x] **Document access control**: added `convex/http.ts`'s `/documents` HTTP action — re-checks `requireAdmin` on every request (via `admin.getDocumentForServing`) and streams the file with `Cache-Control: no-store`, replacing the old unauthenticated, non-expiring `storage.getUrl()` link. The admin claim-detail page now fetches with a Clerk bearer token instead of rendering a bare `<a href>`. A follow-up security review caught that the first version of this endpoint served the file back with the *client-declared* upload Content-Type (stored-XSS risk: a payload that sniffs as a valid PNG could still be uploaded as `Content-Type: text/html`) — fixed by persisting the sniffed (byte-verified) type on the `claimDocuments` row and serving only that, plus `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and a restrictive CSP as defense in depth.
- [x] **Storage-ID ownership binding**: `registerUploadedDocument` now refuses a `storageId` already registered on a *different* claim (`STORAGE_ALREADY_REGISTERED`), via a new `claimDocuments.by_storage` index — closes the overwrite/delete-another-user's-file path without deleting anything on the refusal.
- [x] **Enforce `claimDeadline`**: `submitClaimDocuments` now throws `CLAIM_DEADLINE_PASSED` if the claim's deadline has passed.
- [x] **Confirmation on Approve and Purge**: both now require a `window.confirm()` before firing.
- [x] **Content-type validation is client-asserted**: `registerUploadedDocument` is now a Convex *action* (`convex/lib/fileSniff.ts`'s `sniffFileType`) that reads the file's actual bytes (PNG/JPEG/PDF magic numbers) instead of trusting the browser's declared `Content-Type` header. The ownership/status gate and the actual DB write moved into internal functions (`checkClaimSubmittable`, `finalizeDocumentRegistration`) since actions have no direct `ctx.db` access.
